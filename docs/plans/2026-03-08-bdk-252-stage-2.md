# BDK-252 Stage 2: Store Initialization Tarball — Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> to implement this plan task-by-task.

**Goal:** Build the Nix derivations that produce the initial store
tarball for device provisioning. The tarball contains the Nix store
closure (all packages + dependencies), a pre-built profile generation,
the Nix SQLite database, and config files — everything needed to
bootstrap a device with no prior Nix installation.

**Prerequisites:** Stage 1 complete — `bmc-nix` crate with profile
building, hooks, activation, CLI (`bmc-nix-cli build-profile`),
`nix/widget.nix` for widget packaging, workspace.nix with ARM build
profiles.

**Design decisions:**
- Keep `nix/widget.nix` as-is (no rename to `mkWidgetPackage.nix`)
- Keep `workspace.nix` at repo root (no move to `nix/`)
- Use `closureInfo` + `nix-store --load-db` for tarball creation (not
  `nix copy`; see Research Notes below)

**Tech Stack:** Nix (derivations, closureInfo, builtins.toJSON),
bmc-nix-cli (Rust), gzip

## Research Notes: `nix copy` vs `closureInfo`

The initial thought was to try `nix copy --to local?root=$rootDir` to
create both the store paths and SQLite database in one step. Research
shows this **does not work inside sandboxed Nix builds** — `nix copy`
needs daemon socket access which the sandbox doesn't provide.

The `closureInfo` + `nix-store --load-db` approach is what every
nixpkgs image builder uses (Docker tools, make-system-tarball,
make-ext4-fs). It works inside the sandbox because `nix-store
--load-db` with `NIX_REMOTE=local?root=` operates directly on the
SQLite database without needing the daemon.

**However**, `nix copy --to local?root=...` is simpler for
interactive/development use. If in the future we need a script that
creates a tarball outside of a Nix build (e.g., for CI), this is the
simpler path.

**Reference implementations in nixpkgs:**
- `pkgs/build-support/docker/default.nix` — cleanest example
- `nixos/lib/make-system-tarball.sh` — tarball-specific
- `nixos/lib/make-ext4-fs.nix` — filesystem image

## Subtask 2: Implement `nix/mkIndex.nix`

**Rationale:** Both `mkTarball` and the standalone index build need to
generate `index.json` from a package list. This is a
lightweight derivation — pure JSON generation, no compilation.

**Files:**
- Create: `nix/mkIndex.nix`

### Task 2.1: Implement `mkIndex`

**Signature:**

```nix
# nix/mkIndex.nix
{ pkgs, lib }:
{ packages          # [ { pkg; name; version; category; description;
                    #     upgrade_strategy; install_strategy; } ]
, caches ? []       # [ { name; cache_url; cache_key; } ]
, indexes ? []      # [ "https://..." ] — federated index URLs
, commit ? ""       # git commit hash for provenance field
}:
# Output: derivation producing $out/index.json
```

**Implementation approach:** Use `pkgs.writeText` with
`builtins.toJSON` to generate the JSON. For each package entry, extract
the store path from the `pkg` derivation.

The key expression for extracting a store path string from a derivation:

```nix
builtins.unsafeDiscardStringContext (toString pkg)
```

This strips the build dependency context, giving us just the path
string (e.g., `/nix/store/abc123-hello-1.0.0`) without making the
index derivation depend on building all packages.

**However**, for `mkTarball` the packages DO need to be built (they go
into the tarball). So the `mkIndex` derivation itself doesn't need to
depend on building the packages — it just needs their store path
strings. But when called from `mkTarball`, the packages will already
be built as part of `closureInfo`.

The index JSON schema (from nix-concepts.md):

```json
{
  "version": 1,
  "provenance": { "commit": "<git-hash>" },
  "indexes": [],
  "caches": [
    { "name": "default", "cache_url": "...", "cache_key": "..." }
  ],
  "packages": [
    {
      "name": "...",
      "version": "...",
      "cache": "default",
      "store_path": "/nix/store/<hash>-<name>-<version>",
      "category": "...",
      "description": "...",
      "upgrade_strategy": "...",
      "install_strategy": false
    }
  ]
}
```

**Cache resolution:** If a package entry doesn't specify `cache`, use
the first cache entry's name as default. If `caches` is empty, omit
the `cache` field.

**`upgrade_strategy` and `install_strategy`:** These are passed
through as-is from the package list. They can be strings (`"reboot"`)
or `false`. In Nix, `false` serializes to JSON `false` via
`builtins.toJSON`.

### Task 2.2: Verify the index builds standalone

We can't fully test this until `artifacts.nix` wires it up, but
we can write a simple test in the file itself or verify later in
Subtask 4.

**Success criteria:** `mkIndex` produces valid JSON matching the
schema, with correct store paths extracted from derivations.

## Subtask 3: Implement `nix/mkTarball.nix`

**Rationale:** This is the core deliverable — produces the initial
store tarball for device provisioning.

**Files:**
- Create: `nix/mkTarball.nix`

### Task 3.1: Implement `mkTarball`

**Signature:**

```nix
# nix/mkTarball.nix
{ pkgs, lib, mkIndex }:
{ packages          # same format as mkIndex
, bmc-nix-cli       # derivation of the bmc-nix CLI tool (native build)
, bos_version       # "26.02"
, profile_path ? "/nix/var/nix/gcroots/profiles/bmc"
, extraFiles ? null  # optional derivation whose contents are overlaid
                     # into the tarball root (e.g. /etc/nix/nix.conf)
}:
# Output: derivation producing:
#   $out/nix-<bos_version>.tar.gz
#   $out/metadata.json
```

**Build steps inside the derivation:**

**Step 1: Generate temporary index**

Call `mkIndex` with the same `packages` to produce an index JSON
that `bmc-nix-cli` can consume:

```nix
index = mkIndex {
  inherit packages;
  # No caches needed for local profile building;
  # use a dummy local cache so the CLI can resolve
  caches = [{
    name = "local";
    cache_url = "file:///nix/store";
    cache_key = "local";
  }];
};
```

**Step 2: Set up rootDir and invoke bmc-nix-cli**

```bash
rootDir=$TMPDIR/root

# Build the profile generation inside the tarball root
${bmc-nix-cli}/bin/bmc-nix-cli build-profile \
  --index ${index}/index.json \
  --profile-dir $rootDir${profile_path}
```

This produces the symlink tree at
`$rootDir/nix/var/nix/gcroots/profiles/bmc/bmc-1-link/` with all
packages merged, hooks executed, and manifest written.

**Important:** The profile is NOT activated (no `--activate` flag, no
`current` symlink). On first boot, `bmc-nix-initializer` detects
there is no active profile and activates the latest generation.

**Step 3: Capture closure and populate Nix DB**

```nix
closureInfo = pkgs.closureInfo {
  rootPaths = map (p: p.pkg) packages;
};
```

In the build script:

```bash
# Copy all store paths into the tarball root
while IFS= read -r storePath; do
  cp -a "$storePath" $rootDir/nix/store/
done < ${closureInfo}/store-paths

# Populate the Nix database
export NIX_REMOTE=local?root=$rootDir
export USER=nobody
nix-store --load-db < ${closureInfo}/registration
```

**Step 4: Add profile store paths**

The profile symlink tree at `$rootDir${profile_path}/bmc-1-link/`
contains symlinks pointing into `/nix/store/...`. Those store paths
are already captured by `closureInfo` since it computes the full
closure. However, the hooks might have created files (not symlinks) in
the profile directory that reference store paths not in the original
package list — specifically the hook binaries themselves
(`bmc-hook-merge-files`, etc.) that were invoked during profile build.

We need to ensure the `bmc-nix-cli` derivation's closure is also
included. Add it to `closureInfo.rootPaths`:

```nix
closureInfo = pkgs.closureInfo {
  rootPaths = (map (p: p.pkg) packages) ++ [ bmc-nix-cli ];
};
```

**Step 5: Overlay extraFiles**

```bash
if [ -n "${toString extraFiles}" ]; then
  cp -a ${extraFiles}/* $rootDir/
fi
```

**Step 6: Create tarball**

```bash
tar -czf $out/nix-${bos_version}.tar.gz \
  -C $rootDir \
  --sort=name \
  --mtime='@1' \
  --owner=0 --group=0 \
  --numeric-owner \
  .
```

The `--sort=name --mtime='@1' --owner=0 --group=0` flags improve
reproducibility.

**Step 7: Write metadata.json**

```bash
cat > $out/metadata.json << EOF
{
  "bos_version": "${bos_version}",
  "profile_path": "${profile_path}",
  "tarball_name": "nix-${bos_version}.tar.gz"
}
EOF
```

**nativeBuildInputs:** `nix` (for `nix-store`), `gzip` (for
compression), `bmc-nix-cli` (for profile building).

### Task 3.2: Handle symlinks in the tarball

The profile directory contains symlinks that point to absolute paths
like `/nix/store/abc123.../bin/foo`. When we `tar` the root directory,
these symlinks will be preserved as-is (pointing to absolute paths).
This is correct — after extraction to `/` on the device, the symlinks
will resolve to the actual store paths that are also in the tarball.

Ensure `tar` uses `-h` to NOT follow symlinks (this is the default
for `-c`, but be explicit). Actually, the default `tar -c` behavior
preserves symlinks, which is what we want. Do NOT use `--dereference`.

### Task 3.3: Verify tarball structure

After building, the tarball should contain:

```
./nix/store/...                                    # all closure paths
./nix/var/nix/db/db.sqlite                         # Nix database
./nix/var/nix/gcroots/profiles/bmc/bmc-1-link/     # profile gen 1
./nix/var/nix/gcroots/profiles/bmc/bmc-1-link/bin/ # merged symlinks
./nix/var/nix/gcroots/profiles/bmc/bmc-1-link/lib/ # merged symlinks
./nix/var/nix/gcroots/profiles/bmc/bmc-1-link/manifest
./nix/var/nix/gcroots/profiles/bmc/bmc-1-link/activation/
./etc/nix/nix.conf                                 # from extraFiles
```

**No `current` symlink** — activation happens on device.

**Success criteria:** `nix build .#tarball` succeeds and produces a
valid `.tar.gz` with the structure above. The Nix DB inside is valid
(can be verified by extracting to a temp dir and running
`NIX_REMOTE=local?root=... nix-store --verify`).

## Known risks and mitigations

1. **ARM Nix binary**: Cross-compiling `nix` for ARM may be slow or
   fail. Mitigation: try `armv7Pkgs.nix` first; if it fails, exclude
   it from the package list and note it as a TODO for later.

2. **Sandbox restrictions**: `bmc-nix-cli` runs inside the Nix
   sandbox during `mkTarball`. It must not try to access the network
   or system paths. The CLI's `build-profile` command only does local
   filesystem operations (symlinks, file copies), so this should be
   fine. However, hooks execute binaries — the hook binaries
   (`bmc-hook-merge-files`, etc.) must also be available in the
   sandbox. They're part of the `bmc-nix-cli` derivation, so they
   should be in scope.

3. **Profile hooks finding their binaries**: During profile build, the
   hooks directory contains symlinks to store paths. When
   `bmc-nix-cli` runs hooks, it executes those symlinked binaries. In
   the sandbox, those store paths must be accessible. Since the
   packages are inputs to the derivation (via `closureInfo`), their
   store paths are available. But the hook binaries are part of
   `bmc-nix-cli`, not the packages. Ensure `bmc-nix-cli` is in
   `nativeBuildInputs` so its store path is accessible.

4. **Tarball size**: The full closure of all packages + Nix itself
   could be large. Monitor the output size. For initial development
   this is acceptable.
