One system owner.
Two upgrade paths.

Boser owns firmware and package upgrades on managed miners. BMC presents progress and requests package installation. Deck keeps its existing local upgrade path.

Upgrade ownership and backend boundaries are agreed. External transport, authentication and API/display integration remain to be designed.

01 / What upgrade do we offer?

Check firmware first. Package changes accompany the firmware offer, or become a package-only offer when no firmware upgrade is available.

Starting a firmware upgrade

The firmware upgrade performs the package upgrade too. The displayed package changes are information, not a second package-only operation.

Starting a package-only upgrade

When Start is requested, verify that package-only execution is possible on the current system, then prepare and apply the package update. An earlier offer does not bypass these checks.

02 / Package upgrades use bmc-upgrade

boser-openwrt uses bmc-upgrade to discover and install packages.

Why not use bmc-upgrade for firmware now?

Packages have their own PackageBackend trait and do not require adopting the firmware upgrader. Boser already has image verification, sysupgrade synchronization, platform managers and legacy API callers. Replacing that working path adds a separate migration without being necessary for package support. Share execution ownership and reporting now; leave a firmware refactor for a demonstrated need.

03 / From sysupgrade stderr to observable state

Boser supervises the child independently of the request that started it.

The first Nix-enabled firmware still bootstraps itself. Older Boser need not know Nix exists: initialization stays in the incoming image’s COMMAND. Missing Nix never requires a package-only request first.

04 / One install request. A separate stream to the display.

BMC asks Boser what can be installed, then sends the selected package names. Boser performs the entire update.

Always listening

The display also reflects upgrades started by the Boser FE or scheduler. It does not need a BMC install request to begin watching.

Reconnect without restarting work

Boser immediately sends its current snapshot on subscription. Stream loss does not cancel the upgrade or imply success; BMC shows a disconnected state until it reconnects.

Contract details

Operation names are illustrative; the BMC wire transport remains undecided. Boser owns catalog resolution. Checking caches the selected offer; starting uses the cached package index while rechecking the installed profile. Acceptance is not completion; reconcile a lost response through state rather than blindly retrying.

On package completion, refresh available and installed items. Package completion does not trigger firmware reboot polling. Firmware handoff is Rebooting, not verified reboot success. Widget reload uses the activation signalling path, separately from upgrade-status rendering.

On Boser-managed products, BMC does not execute local upgrades or scheduled profile mutations, with no local fallback. Boser-owned automatic upgrades and GC are handled in the separate mini-miner maintenance work. Deck retains local execution.

05 / One FE contract across architectures

Expose the shared backend operations through transport adapters agreed with the API work, preserving existing firmware clients. The FE consumes the same package-aware contract on every architecture; platform capability determines the available operations.

07 / Service ownership and maintenance

Firmware owns Boser

Package activation manages Nix-owned services. Boser stays in firmware and is not restarted by package upgrades.

Boser owns garbage collection

Boser removes unused store data and old generations on managed miners. Keep cleanup failures distinct from installation failures.

Separate mini-miner maintenance work adds Boser-owned automatic upgrades and GC, targeting the Deck-style two-hour cadence and reusing scheduling code where appropriate. Disable competing BMC autoupgrades as part of that handover. Deck retains its local maintenance.

The maintenance work settles schedule integration and GC policy. BMC API/display integration is separate; the watch remains independent of who requested the upgrade.

Accepted work survives request/watch loss. Proven stopped failure releases the lock; uncertain failure retains it. The watch stores current state, not an event history or durable reboot journal. No cancellation, queue or automatic retry is implied.
