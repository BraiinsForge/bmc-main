# WASM Host Process Model

This document describes how a WASM widget instance becomes a slot inside the shared `bmc-wasm-host` daemon while still
looking like an ordinary per-widget Wayland client to the rest of the system.

For the render scheduling and buffer lifecycle inside the daemon, see [`render-loop.md`](render-loop.md). For static
asset packaging and renderer payload lifetime, see [`renderer-assets.md`](renderer-assets.md).

## Components

WASM widgets use three runtime pieces:

| Component              | Role                                                                                                                                                 | Lifetime                                                                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Widget package wrapper | Shell wrapper generated by `nix/wasm-widgets.nix`; execs `bmc-wasm-thin --wasm <blob> --asset-root <assets> --host-bin <host>`.                      | One executable per packaged WASM widget.                                                                                                                 |
| `bmc-wasm-thin`        | Small process spawned by `WidgetManager`; opens the Wayland socket, connects or starts the host, passes the Wayland fd to the host, then idles.      | One process per widget instance.                                                                                                                         |
| `bmc-wasm-host`        | Shared daemon; owns EGL, the renderer, font cache, a content-keyed compiled-module cache, a table of `WidgetSlot`s, and the in-host system overlays. | One process per WASM SDK major version; started by the first thin, then alive while at least one widget thin **or** one hosted overlay is still running. |

The coordinator and compositor still operate in terms of widget processes. The process they see is the thin wrapper, not
the host daemon. This preserves the existing `SO_PEERCRED`-based identity model in the compositor.

The host also hosts the privileged system overlays compiled into it. They are not widget slots and have no thin — each
is its own Wayland client opened from inside the host process — but they share the host's renderer and event loop and
factor into its lifetime (see [`../system-overlays/`](../system-overlays/), in particular
[the run modes](../system-overlays/README.md#run-modes)). The spawn and control-protocol paths below concern widgets
only; overlays do not start the host and do not use the thin/host control socket.

## Spawn Path

The high-level startup path is:

1. `WidgetManager` spawns the widget binary from the manifest and sets only the Wayland environment: `WAYLAND_DISPLAY`
   and `XDG_RUNTIME_DIR`.
2. For WASM widgets, that binary is a package wrapper. It execs `bmc-wasm-thin` with the absolute `.wasm`, package
   asset-root, and `bmc-wasm-host` paths baked into the Nix store package.
3. `bmc-wasm-thin` opens the compositor Wayland socket directly with `UnixStream::connect`.
4. The thin connects to the host control socket. If no host is accepting, it participates in the startup lock protocol
   and may spawn a detached host daemon.
5. The thin sends a single `Hello { wasm_path }` message to the host control socket and attaches the open Wayland fd
   with `SCM_RIGHTS`.
6. The host receives the fd, creates the Wayland client-side objects, loads the WASM module, builds a `WidgetSlot`, and
   replies with `Ack::Ok`.
7. The thin drops into an idle loop. From this point on, the control socket is only a lifetime witness.

The compositor sees the Wayland connection as belonging to the thin process because peer credentials are latched when
the thin opens the Wayland socket. Passing the fd to the host later does not change those credentials.

## Host Socket And Lock

The default control socket comes from the WASM SDK major version:

```text
/run/bmc/wasm-host-sdk-v{major}.sock
```

The default lockfile is derived from the socket path:

```text
/run/bmc/wasm-host-sdk-v{major}.lock
```

Image-widget fit decodes share a separate device-wide lockfile named `image-decode.lock` in the socket's directory:

```text
/run/bmc/image-decode.lock
```

The file name is fixed within the directory, so hosts for different SDK majors — which run concurrently through an
upgrade — serialize their decodes on the same lock, while a custom `--host-socket` directory gets its own writable,
hermetic lock.

Each fit-decode job holds the shared exclusive lock through decode, resize, cache persistence, and GPU upload. The
decoded RGBA buffer is released before the lock, preventing another host from starting a decode while the prior image
remains in anonymous memory.

The SDK major is `bmc_wasm_protocol::SDK_VERSION.0`. A future incompatible SDK major gets a different socket and
therefore a different host process.

On startup, the thin first tries to connect to the socket:

- Success means an existing host is ready.
- `ENOENT` or `ECONNREFUSED` means host startup is allowed.
- Other connection errors are fatal to the thin.

When startup is allowed, the thin opens the lockfile and tries to take an exclusive non-blocking `flock`.

- If another process owns the lock, this thin waits for a shared lock, then attempts one final host connection.
- If this thin wins the exclusive lock, it checks the socket once more. If the host still is not there, it spawns
  `bmc-wasm-host` and passes the inherited lock fd as `--release-lock-fd`.

The host validates that `--release-lock-fd` points at the lockfile derived from its selected socket path. It binds and
listens on the socket before heavy initialization, then initializes EGL and the shared renderer. Only after that does it
close the release-lock fd. Waiting thins observe the lock release and connect to the ready host.

## Daemon Spawn

`bmc-wasm-thin` starts the host with a double fork:

1. The thin forks an intermediate child.
2. The intermediate child calls `setsid()` and forks the final host grandchild.
3. The intermediate child exits and the original thin reaps it.
4. The grandchild closes inherited fds except the release-lock fd, redirects stdio to `/dev/null`, resets relevant
   signal handlers, and execs `bmc-wasm-host --host-socket <path> --release-lock-fd <fd>`.

The daemon does not depend on the thin that spawned it after exec. It stays alive only because one or more thins keep
control connections open.

## Control Protocol

The thin/host control protocol is intentionally small. It runs over an `AF_UNIX` `SOCK_STREAM` socket and has one
request and one response:

```text
thin -> host: Hello::Load { wasm_path } + one Wayland fd via SCM_RIGHTS
host -> thin: Ack::Ok | Ack::Err(message)
```

The wire format lives in `bmc-wasm-thin-protocol`:

each frame is a 2-byte LE PROTOCOL_VERSION + 4-byte LE length + bincode-encoded payload (HelloMsg / AckMsg), capped at
128 KiB. The Hello::Load frame additionally carries one Wayland fd via SCM_RIGHTS.

After `Ack::Ok`, no more control messages are sent. The host watches the socket for EOF or hangup; the thin watches it
for EOF or hangup as a signal that the daemon is gone.

## Slot Load

For each accepted thin connection, the host:

1. Reads `Hello` and receives exactly one Wayland fd.
2. Wraps the fd in a `wayland_client::Connection`.
3. Binds the Wayland globals it needs, including `deck_widget_manager_v1` and `zwp_linux_dmabuf_v1`.
4. Creates a `wl_surface` and calls `deck_widget_manager_v1.get_widget_surface`.
5. Waits for the initial configure batch: `configure`, `params`, setting events, then `configure_done`.
6. Reads and hashes the `.wasm` bytes, then reuses the cached module for identical content or validates and caches it on
   a miss. Per-function translation into wasmi bytecode stays lazy and populates the shared engine's code map on first
   call.
7. Builds `WasmWidgetRuntime` from that module with the configured width, height, and params.
8. Inserts a `WidgetSlot` in `Dormant` lifecycle state, with no render target.
9. Sends `Ack::Ok` to the thin.

The compositor resolves the widget instance from the Wayland connection's peer PID. Because that PID belongs to the
thin, not the host, the existing coordinator/compositor registration path still works.

## Shutdown And Failure Semantics

The intended lifetime rules are:

- Each widget instance has one thin process for its whole lifetime.
- If the thin exits or is killed, the host sees the control socket close and tears down that slot.
- Slot teardown drops the runtime, releases its compiled-module lease (evicting the cache entry for its final user),
  destroys any render target, drops Wayland objects, and closes the control socket.
- If the host exits, every thin sees control socket hangup and exits.
- The host keeps running while at least one widget slot **or** one hosted overlay is still alive. Only once the last
  slot is gone *and* no overlay is still running does the host wait a short 100 ms grace period and exit.

The grace period avoids immediate respawn churn when one widget exits and another appears a few milliseconds later. It
is not a persistent idle service for widgets.

System overlays change this in practice. They are default-on and stay connected to the compositor for the host's whole
life, so an overlay keeps the host alive after every widget has disconnected — the host is effectively persistent as
long as the compositor is up. The grace-period exit is reached only when there are no widget slots and every overlay has
also disconnected (compositor gone) or been disabled/failed. A failed overlay is shut down and dropped from the host's
list, so a single overlay losing its connection does not by itself end the host while others remain.

Common rejection paths:

- malformed `Hello` or missing/extra fds: host sends `Ack::Err` when possible and drops the connection;
- Wayland configure timeout: slot load fails and the thin exits non-zero after `Ack::Err`;
- WASM load/runtime initialization failure: slot load fails and the thin exits non-zero after `Ack::Err`;
- host readiness timeout: the thin exits non-zero without loading the widget.

## Code Map

- `nix/wasm-widgets.nix` - packages `.wasm` blobs and generates per-widget shell wrappers.
- `bmc/src/widget/manager.rs` and `bmc/src/widget/spawner.rs` - spawn widget binaries and track child PIDs.
- `bmc-wasm-thin/src/lib.rs` - thin process orchestration.
- `bmc-wasm-thin/src/spawn.rs` - host connection, startup lock, and daemonization.
- `bmc-wasm-thin/src/host_client.rs` - `Hello`/`Ack` exchange and idle loop.
- `bmc-wasm-thin/src/wayland_fd.rs` - direct Wayland socket open.
- `bmc-wasm-thin-protocol/src/lib.rs` - wire format, fd passing, socket paths.
- `bmc-wasm-host/src/startup.rs` - host listener setup and release-lock validation.
- `bmc-wasm-host/src/control.rs` - accepting thins and loading slots.
- `bmc-wasm-host/src/module_cache.rs` - content-keyed cache of compiled WASM modules shared across slots.
- `bmc-wasm-host/src/slot.rs` - per-widget slot setup, dispatch, render, and teardown.
- `bmc-wasm-host/src/overlays.rs` - building, env-gating, prewarming, and rendering the in-host system overlays.
- `bmc-wasm-host/src/main_loop.rs` - daemon main loop and host lifetime grace period (kept alive by slots and overlays).
