# WASM Host Process Model

This document describes how a WASM widget instance becomes a slot inside the shared `bmc-wasm-host` process while still
looking like an ordinary per-widget Wayland client to the rest of the system.

For the render scheduling and buffer lifecycle inside the host, see [`render-loop.md`](render-loop.md). For static asset
packaging and renderer payload lifetime, see [`renderer-assets.md`](renderer-assets.md).

## Components

WASM widgets use three runtime pieces:

| Component              | Role                                                                                                                                                           | Lifetime                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Widget package wrapper | Shell wrapper generated by `nix/wasm-widgets.nix`; execs `bmc-wasm-thin --wasm <blob> --asset-root <assets>`.                                                  | One executable per packaged WASM widget.                                                                     |
| `bmc-wasm-thin`        | Small process spawned by `WidgetManager`; opens the Wayland socket, waits for the host, passes the Wayland fd to it, then idles.                               | One process per widget instance.                                                                             |
| `bmc-wasm-host`        | Shared process; owns EGL, the renderer, font cache, a content-keyed compiled-module cache, a table of `WidgetSlot` instances, and the in-host system overlays. | One compositor-supervised process for the active WASM SDK major, independent of the configured widget count. |

The coordinator registers each configured widget with the compositor under its stable instance key before spawning the
thin. The thin receives that key in `BMC_WIDGET_KEY` and passes it to the host, which uses it when requesting the widget
surface. This is trusted native routing identity, not a secret or a security boundary: it selects a retained compositor
record, while activation state decides whether that record currently accepts a connection.

The host also hosts the privileged system overlays compiled into it. They are not widget slots and have no thin — each
is its own Wayland client opened from inside the host process — but they share the host's renderer and event loop (see
[`../system-overlays/`](../system-overlays/), in particular [the run modes](../system-overlays/README.md#run-modes)).
The compositor starts the host independently of widgets, so overlays are available even when no widget is configured.
They use the compositor-provided `WAYLAND_DISPLAY` but do not use the thin/host control socket.

`/etc/bmc_system.json` is firmware-owned packaging state rather than user configuration under `/etc/bmc`. The system
config, thin launcher, and host are executable dependencies of the compositor service. Changing any of them restarts the
compositor and loads the activated command list; widget-only activation keeps the running host intact.

## Spawn Path

The high-level startup path is:

1. After binding its Wayland socket, the compositor starts the commands configured under `compositor.commands` in
   `/etc/bmc_system.json`. The production configuration starts `bmc-wasm-host`; the supervisor supplies the bound socket
   name in `WAYLAND_DISPLAY`, restarts the host with bounded backoff, and stops it before tearing down Wayland.
2. The host binds its SDK-major control socket and its compiled-in overlays connect to `WAYLAND_DISPLAY`.
3. The coordinator registers and activates each configured widget in the compositor. `WidgetManager` then spawns the
   widget binary from the manifest with `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, and the stable configured-instance key in
   `BMC_WIDGET_KEY`.
4. For WASM widgets, that binary is a package wrapper. It execs `bmc-wasm-thin` with the absolute `.wasm` and package
   asset-root paths baked into the Nix store package.
5. `bmc-wasm-thin` opens the compositor Wayland socket directly with `UnixStream::connect`, then waits up to its host
   readiness deadline for the host control socket. It never starts or replaces a host.
6. The thin sends a single `Hello::Load { widget_key, wasm_path, asset_root }` message to the host control socket and
   attaches the open Wayland fd with `SCM_RIGHTS`.
7. The host receives the fd, creates the Wayland client-side objects, loads the WASM module, builds a `WidgetSlot`, and
   replies with `Ack::Ok`.
8. The thin drops into an idle loop. From this point on, the control socket is only a lifetime witness. Each thin owns
   exactly one such connection, and each accepted connection corresponds to at most one host slot.

The host passes the stable key to `deck_widget_manager_v2.get_widget_surface`. The compositor either attaches the client
to the matching active retained record or rejects it immediately. It does not buffer unclaimed Wayland connections for
future registrations; registration and activation happen before the process is spawned.

## Host Socket And Decode Lock

The default control socket comes from the WASM SDK major version:

```text
/run/bmc/wasm-host-sdk-v{major}.sock
```

Image-widget fit decodes share a separate device-wide lockfile named `image-decode.lock` in the socket's directory:

```text
/run/bmc/image-decode.lock
```

The file name is fixed within the directory, so hosts for different SDK majors serialize their decodes if they run
concurrently, while a custom `--host-socket` directory gets its own writable, hermetic lock.

Each fit-decode job holds the shared exclusive lock through decode, resize, cache persistence, and GPU upload. The
decoded RGBA buffer is released before the lock, preventing another host from starting a decode while the prior image
remains in anonymous memory.

The SDK major is `bmc_wasm_protocol::SDK_VERSION.0`. A future incompatible SDK major gets a different socket and host
command. On a compositor restart, SIGTERM ends the host without unwinding, so the next host normally removes the stale
socket before binding. A live listener instead makes the new host fail. Thins only retry `ENOENT` and `ECONNREFUSED`
until their readiness deadline; other connection errors fail immediately.

## Control Protocol

The thin/host control protocol is intentionally small. It runs over an `AF_UNIX` `SOCK_STREAM` socket and has one
request and one response:

```text
thin -> host: Hello::Load { widget_key, wasm_path, asset_root } + one Wayland fd via SCM_RIGHTS
host -> thin: Ack::Ok | Ack::Err(message)
```

`Hello::Load` also carries the stable `widget_key` and optional `asset_root`. The key is copied from `BMC_WIDGET_KEY`;
it is routing identity for the configured instance, not an authentication credential.

The wire format lives in `bmc-wasm-thin-protocol`:

each frame is a 2-byte LE PROTOCOL_VERSION + 4-byte LE length + bincode-encoded payload (HelloMsg / AckMsg), capped at
128 KiB. The Hello::Load frame additionally carries one Wayland fd via SCM_RIGHTS.

After `Ack::Ok`, no more control messages are sent. The host watches the socket for EOF or hangup; the thin watches it
for EOF or hangup as a signal that the host is gone.

## Slot Load

The listener is non-blocking and drains every queued connection after a wake. Each accepted connection becomes an
independent pending admission rather than blocking the event loop:

- `AwaitHello` incrementally receives the framed hello and its single fd, with its own 250 ms deadline.
- `AwaitConfigure` polls both the control socket and that admission's Wayland fd while the keyed surface request waits
  for `configure_done`, with its own 10 s deadline.
- once configure is ready, only that admission performs module/runtime loading and becomes an established slot.

The main loop processes established control sockets first, then pending control sockets, newly accepted connections,
pending configure/load work, and only then established widget work. A silent partial hello or configure therefore does
not block another admission's progress, and a closed established control is handled before its slot can process another
Wayland event or render.

For each admitted thin connection, the host:

1. Reads `Hello` and receives exactly one Wayland fd.
2. Wraps the fd in a `wayland_client::Connection`.
3. Binds the Wayland globals it needs, including `deck_widget_manager_v2` and `zwp_linux_dmabuf_v1`.
4. Creates a `wl_surface` and calls `deck_widget_manager_v2.get_widget_surface` with the stable widget key.
5. Waits for the initial configure batch: `configure`, `params`, setting events, then `configure_done`.
6. Reads and hashes the `.wasm` bytes, then reuses the cached module for identical content or validates and caches it on
   a miss. Per-function translation into wasmi bytecode stays lazy and populates the shared engine's code map on first
   call.
7. Builds `WasmWidgetRuntime` from that module with the configured width, height, and params.
8. Inserts a `WidgetSlot` in `Dormant` lifecycle state, with no render target.
9. Sends `Ack::Ok` to the thin.

Pending admissions remain host-local. The compositor retains configuration and connection mode by stable key, but has no
pending-connection table: an unknown or inactive key is rejected by the protocol request.

## Shutdown And Failure Semantics

The intended lifetime rules are:

- The compositor supervisor owns the host as a direct child. It terminates the host's process group before dropping the
  Wayland display and restarts an unexpected host exit with bounded backoff.
- A widget instance has one thin process at a time. The instance outlives it: bmc supervises the thin as an ordinary
  widget child, so an exit it did not ask for is followed by a respawn on a backoff ladder — see "Crash supervision" in
  [`widget-runtime-configuration.md`](../widget-runtime-configuration.md).
- If the thin exits or is killed, the host sees the control socket close and tears down that slot.
- Slot teardown drops the runtime, releases its compiled-module lease (evicting the cache entry for its final user),
  destroys any render target, drops Wayland objects, and closes the control socket.
- If the host exits, every thin sees control socket hangup and exits. Widget supervision respawns the thins, which wait
  for the compositor supervisor to provide the next host.
- The host keeps running independently of established slots, pending admissions, and hosted overlays. Only the
  compositor supervisor ends it, after first stopping its process group and before tearing down the Wayland display.

Admission handling is terminal and exact. Each pass partitions admissions into still pending, loaded, or rejected;
loaded slots and rejected attempts are handled once, then removed from the pending set.

System overlays are default-on and keep their own Wayland connections for the host's whole life. A failed overlay is
shut down and dropped from the host's list without changing host lifetime; widgets and the other overlays keep running.

Common rejection paths:

- malformed `Hello` or missing/extra fds: host sends `Ack::Err` when possible and drops the connection;
- invalid, unknown, or inactive widget key: admission fails and the thin exits non-zero after `Ack::Err`;
- Wayland configure timeout: slot load fails and the thin exits non-zero after `Ack::Err`;
- WASM load/runtime initialization failure: slot load fails and the thin exits non-zero after `Ack::Err`;
- host readiness timeout: the thin exits non-zero without loading the widget.

None of these end the instance. Supervision reads any exit it did not request as a crash and retries, so a thin that
fails this way reappears rather than leaving the cell empty — and a fault that keeps recurring shows up as a widget
returning on a lengthening delay, not as one that never comes back. Exit status carries no policy signal either way: a
thin exits 0 when its host dies, which is the ordinary fleet-wide failure.

## Code Map

- `nix/wasm-widgets.nix` - packages `.wasm` blobs and generates per-widget shell wrappers.
- `bmc/src/widget/manager.rs` and `bmc/src/widget/spawner.rs` - spawn and supervise widget binaries.
- `bmc-wasm-thin/src/lib.rs` - thin process orchestration.
- `bmc-wasm-thin/src/host_connect.rs` - bounded wait for the compositor-owned host.
- `bmc-wasm-thin/src/host_client.rs` - `Hello`/`Ack` exchange and idle loop.
- `bmc-wasm-thin/src/wayland_fd.rs` - direct Wayland socket open.
- `bmc-wasm-thin-protocol/src/lib.rs` - wire format, fd passing, socket paths.
- `bmc-wasm-host/src/startup.rs` - host listener setup and stale-socket recovery.
- `bmc-wasm-host/src/control.rs` - accepting thins and loading slots.
- `bmc-wasm-host/src/module_cache.rs` - content-keyed cache of compiled WASM modules shared across slots.
- `bmc-wasm-host/src/slot.rs` - per-widget slot setup, dispatch, render, and teardown.
- `bmc-wasm-host/src/overlays.rs` - building, env-gating, prewarming, and rendering the in-host system overlays.
- `bmc-wasm-host/src/main_loop.rs` - control-first dispatch, pending admission polling, and host lifetime/exit sweep.
